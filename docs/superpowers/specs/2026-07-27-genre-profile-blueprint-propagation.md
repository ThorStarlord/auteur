# Genre Profile–to–Blueprint Propagation Specification

## Status

Proposed / awaiting approval

## Problem

GenreProfileCommitment is a canonical, author-accepted Layer 1 commitment
stored on StoryIdentity, but compile_to_blueprint() does not read it, so
accepted profile commitments have no observable structural effect in the
derived Blueprint.

## Proven evidence

Audit report (C:\Users\Admin\AppData\Local\Temp\opencode\audit_report.md)
established empirically at commit 6b01267:

- **Pair 1 — Romance vs Grimdark**: 74 differing blueprint fields. Base
  identity fields propagate correctly.
- **Pair 2 — Same identity, WITH erotic_fiction genre_profile vs WITHOUT**:
  **0 differing fields**. The entire GenreProfileCommitment has zero
  structural effect. Confirmed gap.
- **Pair 3 — Same premise, target_experience "dread" vs "hope"**: Act tones
  differ correctly. Target experience propagates.

Call flow confirms:

```
compile_to_blueprint(identity)
  → reads title, central_engine, target_experience, story_type.*
  → NEVER reads identity.genre_profile
```

Reconcile path confirms partial mutation:

```
reconcile_identity_with_recommendation(identity, rec)
  → sets identity.genre_profile = commitment
  → mutates story_type.genre (from pack_id)
  → mutates story_type.subgenres (from profile_id)
  → mutates target_experience (from first emotion key)
  → Does NOT propagate accepted_narrative_engine,
    accepted_framing, accepted_resolution_contract
```

Distinctions:
- **Proven fact**: compile_to_blueprint() reads zero genre_profile fields.
- **Architectural interpretation**: GenreProfileCommitment is Layer 1
  (Identity) but its content is structurally ignored at the Layer 1→2 boundary.
- **Proposed solution**: Define propagation contract for one commitment type.
- **Unresolved product decision**: Which commitment types propagate, at what
  authority level, with what override semantics.

This is not a general "Identity-to-Structure propagation failure." Base
StoryIdentity fields (title, story_type, central_engine, target_experience)
already propagate. The gap is specifically:

**Genre Profile–to–Blueprint propagation**

## Authority model

| Artifact | Authority level |
|---|---|
| GenreRecommendation | **Advisory**. Causes zero mutation before explicit acceptance. May be discarded by the author. Stored as a non-canonical working artifact. |
| GenreProfileCommitment | **Canonical Layer 1** once explicitly accepted and stored on StoryIdentity. Carries the same authority as any other StoryIdentity field. |
| StoryIdentity | **Canonical Layer 1 authority**. Sole source of authorial commitments. All downstream artifacts derive from it. |
| StoryBlueprint | **Derived Layer 2 artifact**. Compiled deterministically from StoryIdentity. Author-editable after compilation, but the identity remains the canonical source. |
| Structural proposal | **Working artifact**. Generated by the structure engine as a suggestion. Requires author acceptance before becoming Structural commitment. |
| Structural diagnostic | **Read-only Layer 2 finding**. Reports coherence or completeness issues against identity commitments and structural rules. Never mutates state. |
| Generated realization artifact | **Derived Layer 3+**. Produced from the Blueprint. Not authoritative for structure or identity. |

Rules:

1. **GenreProfileCommitment is canonical because it was explicitly accepted**
   through the documented confirm path (CLI `accept` with `--confirm`).
   It is not advisory — it is a stored author commitment with the same
   authority as a hand-edited StoryIdentity field.

2. **Blueprint is derived but independently author-editable**. After
   compilation, the author may edit the Blueprint YAML directly. The identity
   remains the canonical source; divergence is detected by diagnostics.

3. **Compilation may deterministically derive obligations from accepted
   profile commitments**. These obligations must be:
   - Deterministic (same identity → same Blueprint)
   - Traceable (provenance points to the commitment)
   - Explainable (diagnostics reference the commitment)
   - Overridable (author edits to Blueprint take precedence)

4. **Profile data that may constrain Blueprint generation**: accepted
   resolution contract, accepted narrative engine, accepted target emotions
   (subset), accepted framing. These have defined schemas with enumerable
   values or structured patterns.

5. **Profile data that must remain advisory**: adherence posture (affects
   diagnostic severity, never structure), author rationale fields, confidence
   metadata, recommendation provenance IDs (traceability only).

6. **Operations requiring additional author confirmation**:
   - Accepting a recommendation → explicit `--confirm`
   - Overriding a profile commitment → explicit `--confirm`
   - Mutating Layer 1 after Blueprint creation → staleness detection

7. **Author override interaction**: GenreAuthorOverride entries on the
   profile commitment modify how that commitment compiles to the Blueprint.
   They are not silent — they are stored with provenance and rationale.
   They are distinct from StoryIdentity.author_overrides.

8. **If the profile is later removed or replaced**: The Blueprint retains its
   current state but becomes stale. A regeneration from the updated identity
   produces a new Blueprint reflecting the new profile. Diagnostics detect
   the divergence.

**StoryIdentity remains canonical Layer 1 authority.** No generation or
diagnostic step silently mutates StoryIdentity. Profile acceptance is an
explicit author action with atomic persistence.

## Commitment classification

Field-by-field analysis of GenreProfileCommitment (models.py:214-228):

### primary_pack_id, primary_pack_version, pack_content_hash
**Role: Traceability metadata**

These identify which Genre Pack and version produced the commitment. They
must survive downstream so diagnostics can check pack validity, but they
should not alter Blueprint behavior directly.
- Why not structural: The pack identity is context, not an obligation.
- Why not identity-only: Diagnostics need to validate that the pack still
  exists and the content hash matches.

### primary_profile_id
**Role: Structural constraint**

The accepted subgenre profile ID directly affects which structural patterns,
templates, and defaults apply. Currently this is partially propagated (it
sets `story_type.subgenres`), but full structural implications are not
derived.
- Rationale: The profile ID selects a specific set of structural
  expectations (resolution patterns, narrative engines, emotional targets)
  from the Genre Pack. This is a deterministic structural constraint.

### secondary_genres
**Role: Identity-only context**

Secondary genre tags are authorial context that influence no deterministic
structural rule. They exist on the identity for reference.
- Why not structural: No field in Blueprint maps to "secondary genres."
  Adding one would introduce speculative schema without proven need.

### accepted_target_emotions: dict[str, float]
**Role: Structural proposal source**

Weighted emotional targets from the profile. These currently partially
propagate via target_experience mutation during reconciliation, but the
full weighted set is lost.
- Why proposal source: Weights imply relative importance, which is a
  recommendation the author may reconfirm or adjust. The first emotion key
  already writes to target_experience.primary — this is the correct pattern.
  The full weighted set should not override explicit target_experience but
  can populate secondary_palette and emotional_trajectory.
- The weights themselves (float values) are metadata, not structural
  constraints.

### accepted_narrative_engine: str
**Role: Structural constraint**

The narrative engine ID (e.g., "erotic_identity_transformation") selects a
specific narrative machinery pattern from the Genre Pack. This should
specialize or constrain the main story_engine in the Blueprint.
- Rationale: A narrative engine family defines core conflict patterns,
  escalation structures, and resolution expectations. This is deterministic
  — given an engine ID, the system knows which structural patterns to apply.

### accepted_framing: FramingCommitment
**Role: Diagnostic expectation**

Framing (primary: str, secondary: list[str]) describes tonal and
presentational choices. It does not directly generate structural obligations
but creates expectations that downstream artifacts should satisfy.
- Why not structural: "Romantic framing" does not map to a specific
  structural element like a thread or beat. It maps to tonal/expression
  choices that diagnostics can check.
- Diagnostic use: If the framing is "unsettling" but emotional_design
  describes "uplifting" tones, a diagnostic fires.

### accepted_resolution_contract: ResolutionContractCommitment
**Role: Structural constraint**

This is the strongest structural candidate. It defines:
- pattern: str — named pattern (e.g., "transformative_resolution",
  "relational_fulfillment", "dark_transgression_resolution")
- required_outcomes: list[str] — outcomes the resolution must deliver
- rejected_outcomes: list[str] — outcomes the resolution must avoid

The resolution pattern maps directly to Blueprint contract obligations:
mandatory_ending_tone, expected_elements, and thematic resolution tracking.
- Rationale: A resolution pattern implies concrete structural commitments
  about the ending. The system can deterministically derive which elements
  must appear in AuthorAudienceContract.expected_elements and whether the
  ending_tone aligns.

### adherence_posture: AdherencePosture
**Role: Diagnostic expectation**

The posture (CONVENTIONAL, FLEXIBLE, REVISIONIST, SUBVERSIVE,
DECONSTRUCTIVE) determines how violations of profile commitments are
reported. It does not change structure.
- Why not structural: All five values produce the same Blueprint from the
  same profile. The posture only affects diagnostic severity and
  explanation language.
- See "Adherence posture semantics" section for full details.

### source_recommendation_id: str | None
**Role: Traceability metadata**

Links the commitment to the original GenreRecommendation. Must survive for
provenance queries but never affects Blueprint content.

### author_overrides: list[GenreAuthorOverride]
**Role: Structural constraint (conditional)**

Each override specifies:
- target_expectation: str — which commitment field is overridden
- recommended_value: str — what the profile originally said
- replacement_value: str — what the author changed it to
- author_rationale: str — why
- replacement_function: str — optional functional description

When present, the override replaces the profile-derived obligation during
compilation. The original recommendation value remains inspectable via
provenance.
- Rationale: This IS a structural constraint — it directly changes what
  gets compiled. But it's conditional on author action.

### accepted_at: str | None
**Role: Traceability metadata**

Timestamp of acceptance. Useful for staleness checks. No structural effect.

## Conflict-precedence policy

**Recommended: Policy 3 (profile provides defaults) with explicit
diagnostics for conflicts.**

Statement: Accepted profile commitments fill missing values and generate
proposals for populated fields. They never silently override explicit
author-authored values. When a profile commitment conflicts with an existing
StoryIdentity field, a diagnostic is emitted identifying the conflict and
recommending resolution.

Specific rules:

### accepted_narrative_engine vs central_engine
- Profile provides narrative engine family (which defines core conflict
  type, escalation pattern). This specializes but does not replace
  central_engine's five structural forces.
- If the narrative engine's core_conflict is incompatible with
  central_engine.conflict, emit WARNING diagnostic.
- central_engine values always win; the profile engine becomes an advisory
  annotation on story_engine.

### accepted_target_emotions vs target_experience
- Profile emotions fill missing target_experience fields (secondary_palette,
  emotional_trajectory). They never overwrite target_experience.primary or
  .progression if explicitly authored.
- If the first emotion key differs from target_experience.primary, emit
  INFO diagnostic noting the divergence.
- During initial reconciliation (reconcile_identity_with_recommendation),
  target_experience IS written from the first emotion key. This is the one
  exception — it happens at acceptance time, not compilation time, and is
  visible to the author before confirmation.

### accepted_resolution_contract vs existing ending/change commitments
- Resolution contract required_outcomes populate
  AuthorAudienceContract.expected_elements if empty.
- If expected_elements is already populated, the contract adds WARNING
  diagnostics for each missing required outcome.
- The resolution pattern constrains mandatory_ending_tone selection only if
  ending_tone was not explicitly set. If mode is explicitly set, mode wins.

### accepted_framing vs mode
- Framing is diagnostic-only. If the accepted framing primary is
  incompatible with the story mode, emit WARNING.
- Example: mode=TRAGIC with framing.primary="romantic" may be contradictory.

### adherence_posture vs author overrides
- Adherence posture determines diagnostic severity but never overrides
  author intent. An author override on a field takes precedence regardless
  of posture.

### profile obligations vs genre_contract_snapshot
- Profile obligations are checked against genre_contract_snapshot during
  validation. Conflicts emit diagnostics. The contract snapshot is the
  authoritative definition of genre constraints.

### profile-derived defaults vs explicit author-authored values
- Author-authored values always win. A profile-derived value is never
  silently written over an explicit value.
- "Explicit" means: the field was present in the YAML before compilation,
  or the field was set by a prior author action (e.g., identity init CLI).

Requirements met:
- **No silent conflict resolution**: Every conflict between profile and
  identity is reported.
- **Deterministic output**: Same identity → same Blueprint regardless of
  profile acceptance path.
- **Author-visible diagnostics**: Every conflict has a diagnostic.
- **Preserved provenance**: Profile source is tracked.
- **Stable serialization**: Adding profile propagation does not change
  serialization of identities without profile.
- **Backward compatibility**: Identities without genre_profile compile
  identically to current v0.37.1 behavior.

## Selected vertical slice

**Candidate A — accepted_resolution_contract**

Chosen based on evidence:

1. **Structural determinism**: ResolutionContractCommitment has three
   precisely defined fields (pattern, required_outcomes, rejected_outcomes)
   with enumerable/structured values. No NLP required.

2. **Visible user value**: Authors who accept a genre profile currently see
   zero structural effect. Adding resolution obligation propagation means
   the Blueprint's AuthorAudienceContract.expected_elements would contain
   concrete requirements derived from the profile. This is immediately
   meaningful.

3. **Minimal schema expansion**: AuthorAudienceContract already has
   expected_elements, mandatory_ending_tone, and forbidden_tropes. The
   resolution contract maps directly to these. No new Blueprint section is
   strictly required (though a provenance structure is recommended).

4. **Testable without literary judgment**: "Does expected_elements contain
   the required outcomes from the profile?" is a structural equality check.

5. **Preserves author authority**: Author can edit expected_elements after
   compilation. Diagnostics flag missing elements without blocking.

6. **Proves the complete chain**:
   Recommendation → acceptance → commitment → compilation → Blueprint
   → diagnostic. Every link is exercised.

7. **No unrestricted NLP**: Pattern matching is by ID, not by semantic
   prose matching.

Rejected candidates:

- **accepted_narrative_engine** (Candidate B): Requires a mapping from
  engine ID to structural force modifications. The current engine system
  uses archetypal force_map tuples. Adding engine specialization would
  require expanding `synthesize_structural_forces` or adding engine-specific
  templates. Doable but more scope than needed for the first slice.

- **accepted_target_emotions** (Candidate C): Weighted emotional targets
  are partially propagated already (first key → target_experience.primary).
  Full weighted set propagation requires emotional_design expansion, which
  has higher literary-quality judgment risk. Better done after the
  resolution contract proves the propagation machinery.

## Blueprint representation

**Recommended: Option B (integrate into existing fields) with minimal
provenance annotation.**

### Option evaluation

| Criterion | Option A (dedicated section) | Option B (integrate + provenance) | Option C (normalized obligations) |
|---|---|---|---|
| Semantic clarity | High — profile obligations are explicit | Medium — mixed with author values | High — one canonical structure |
| Schema stability | Low — new section per commitment type | High — reuses existing contract fields | Medium — new structure, but stable |
| Duplication risk | Low | Medium — mixing sources requires provenance | Low |
| Traceability | Medium — section-level | High — field-level via provenance | High — obligation-level |
| Diagnostic usability | Medium — separate section to check | High — same fields author edits | High — one check surface |
| Serialization compat | Breaking — new required section | Additive — new field never required | Additive if optional |
| Genre Pack extensibility | Medium — new section per pack field | High — reuses contract extension pattern | High — new obligation types |
| Author editability | Medium — separate section | High — edits same fields they always edit | Medium — separate structure |
| Migration cost | Higher — tests expect schema shape | Lower — additive field, no migration | Lower — optional field |

### Recommended design

**No new top-level Blueprint section.** Instead:

1. **Profile-derived values integrate into AuthorAudienceContract**:
   - `expected_elements` gains profile-required outcomes
   - `forbidden_tropes` gains profile-rejected outcomes
   - `mandatory_ending_tone` is constrained by pattern if unset

2. **A lightweight provenance field on StoryBlueprint**:

```python
class ProfileDerivation(BaseModel):
    source_field: str  # e.g., "genre_profile.accepted_resolution_contract"
    recommendation_id: str | None
    derived_at: str  # ISO timestamp of compilation
    obligations_applied: list[str]  # which obligation IDs were derived

# Added to StoryBlueprint:
profile_derivation: ProfileDerivation | None = None
```

This avoids copying the raw commitment blob while providing full
traceability for every derived obligation.

3. **Field-level annotation via structured comments in YAML** is not
   practical for Pydantic. Instead, the provenance field records what was
   derived and from where. Diagnostics use this to explain findings.

### Example Blueprint output fragment


## Traceability model

Every profile-derived Blueprint value must answer these questions:

| Question | Mechanism |
|---|---|
| Which commitment caused this? | ProfileDerivation.source_field |
| Which profile & recommendation? | ProfileDerivation.recommendation_id → GenreRecommendation |
| Accepted directly or via override? | GenreProfileCommitment.author_overrides contains the override; ProfileDerivation.obligations_applied includes override flag |
| Was the obligation modified by author? | Compare ProfileDerivation with current Blueprint field value — if different, author edited |
| Is it active, waived, or contradicted? | Diagnostic checks profile obligation vs resolved field; override status from author_overrides |
| Which diagnostic refers to it? | Diagnostic.genre_recommendation_flow contains profile_derivation.source_field |

**Provenance fields are stable identifiers and schema paths**, not line
numbers or duplicate prose.

The GenreRecommendation (stored as JSON in
`.auteur/genre_recommendations/<id>.json`) is the canonical source for
full recommendation context. The Blueprint stores only the derivation
summary — enough to trace, not enough to duplicate.

## Adherence posture semantics

AdherencePosture (models.py:18-23) has five values:

| Posture | Structural effect | Diagnostic severity |
|---|---|---|
| CONVENTIONAL | Same structure as any other posture | Profile violation → ERROR |
| FLEXIBLE | Same structure | Profile violation → WARNING |
| REVISIONIST | Same structure | Profile violation → WARNING + INFO note that revision is intentional |
| SUBVERSIVE | Same structure | Profile violation → WARNING + INFO note about intentional subversion |
| DECONSTRUCTIVE | Same structure | Profile violation → INFO (expected consequence of deconstruction) |

Rules:
- **Posture NEVER changes compiled structure.** The same profile with any
  posture produces the same Blueprint.
- **Posture ONLY affects diagnostic severity and explanation language.**
- **Author override suppresses posture-based severity reduction.**
  If a field is overridden, the override rationale replaces the
  posture-based explanation.
- **Compilation always proceeds** regardless of posture. No posture blocks
  Blueprint generation.
- **Proposal generation is unaffected** by posture.
- **Diagnostics explain the posture** in their message:

  > "The accepted profile commits to X (adherence posture: FLEXIBLE).
  > The Blueprint currently lacks Y. This is flagged as a WARNING because
  > the posture allows flexibility. Resolve by adding Y or accepting the
  > gap."

Gap identified: The current code never reads adherence_posture. The
severity-modification logic described above would need to be implemented
in the diagnostic layer, not in compilation.

## Diagnostic contract

For the accepted_resolution_contract vertical slice:

### D-RES-001: Missing required outcome

| Property | Value |
|---|---|
| **Stable ID** | `profile.resolution_contract.missing_required_outcome` |
| **Trigger** | A required outcome from accepted_resolution_contract.required_outcomes is absent from AuthorAudienceContract.expected_elements |
| **Severity** | ERROR (CONVENTIONAL), WARNING (FLEXIBLE/REVISIONIST/SUBVERSIVE), INFO (DECONSTRUCTIVE) |
| **Required evidence** | List of missing outcomes, accepted_resolution_contract.source_recommendation_id, ProfileDerivation.source_field |
| **Originating commitment path** | `identity.genre_profile.accepted_resolution_contract.required_outcomes` |
| **Affected Blueprint path** | `contract.expected_elements` |
| **Explanation** | "The accepted profile (source: rec_abc123) requires outcome[s] {X} in the resolution, but the Blueprint's expected_elements does not include {X}. This weakens the profile's resolution contract." |
| **Suggested repair** | "Add '{X}' to contract.expected_elements, or add a GenreAuthorOverride for 'accepted_resolution_contract.required_outcomes' with a rationale." |
| **Author-override behavior** | If a GenreAuthorOverride exists for `accepted_resolution_contract.required_outcomes`, the diagnostic is suppressed (the override rationale explains the divergence). |
| **False-positive risk** | None. This is a structural set membership check. |

### D-RES-002: Rejected outcome present

| Property | Value |
|---|---|
| **Stable ID** | `profile.resolution_contract.rejected_outcome_present` |
| **Trigger** | A rejected outcome from accepted_resolution_contract.rejected_outcomes is present in AuthorAudienceContract.expected_elements or not in forbidden_tropes |
| **Severity** | ERROR (CONVENTIONAL), WARNING (FLEXIBLE/REVISIONIST/SUBVERSIVE), INFO (DECONSTRUCTIVE) |
| **Required evidence** | List of present rejected outcomes, provenance references |
| **Originating commitment path** | `identity.genre_profile.accepted_resolution_contract.rejected_outcomes` |
| **Affected Blueprint path** | `contract.expected_elements` or `contract.forbidden_tropes` |
| **Explanation** | "The accepted profile rejects outcome '{X}', but the Blueprint's expected_elements contains it (or forbidden_tropes does not exclude it)." |
| **Suggested repair** | "Remove '{X}' from expected_elements or add it to forbidden_tropes, or add a GenreAuthorOverride." |
| **False-positive risk** | None. |

### D-RES-003: Resolution pattern conflicts with ending tone

| Property | Value |
|---|---|
| **Stable ID** | `profile.resolution_contract.ending_tone_conflict` |
| **Trigger** | The resolution pattern implies an ending tone that contradicts mandatory_ending_tone (when mode is not explicitly TRAGIC/COMIC/other) |
| **Severity** | WARNING |
| **Required evidence** | Pattern name, resolved ending tone, profile provenance |
| **Originating commitment path** | `identity.genre_profile.accepted_resolution_contract.pattern` |
| **Affected Blueprint path** | `contract.mandatory_ending_tone` |
| **Explanation** | "The accepted resolution pattern '{pattern}' typically requires a {expected_tone} ending, but the Blueprint declares '{actual_tone}'. This may create audience expectation mismatch." |
| **Suggested repair** | "Align ending tone with the pattern, add a GenreAuthorOverride, or change the resolution contract." |
| **False-positive risk** | Low. Patterns have known tone associations, but an author may intentionally subvert. Override mechanism handles this. |

### Diagnostic shape (all three)

```
The accepted profile commits the story to resolution pattern X with required
outcomes [Y] and rejected outcomes [Z]. The Blueprint currently contains or
lacks [...]. This weakens or contradicts the accepted resolution contract.
Resolve by adding, revising, explicitly overriding, or waiving the obligation.
```

No claim that the story is "good" or "bad." No broad lexical matching
where structural field checks are possible.

## Backward compatibility

| Scenario | Behavior |
|---|---|
| Identity without genre_profile | compile_to_blueprint() unchanged. No profile_derivation on Blueprint. Existing tests pass identically. |
| Identity created before v0.37.0 | No genre_profile field → same as above. Schema defaults apply. |
| Existing Blueprints without profile-derived fields | Blueprint remains valid. Regeneration from same identity (without profile) produces identical output. Regeneration with profile adds profile_derivation field. |
| Profile removed after Blueprint creation | Blueprint retains current state. Diagnostics detect staleness. Profile remains inspectable via identity. |
| Profile changed after Blueprint creation | Next compilation uses new profile. Blueprint from old profile is "stale" — diagnostics flag divergence between profile obligations and current Blueprint. |
| Recommendation accepted but Blueprint not regenerated | Profile is stored on identity. Blueprint is stale but valid. Diagnostics flag missing profile obligations. |
| Author-edited Blueprint obligations | Author edits to expected_elements or forbidden_tropes take precedence. Diagnostics compare resolved fields against profile, not against the derived value. |
| Author override replacing one profile commitment | GenreAuthorOverride on the commitment. Compilation uses replacement_value for that field. Provenance records the override. Diagnostics honor it. |
| Invalid or incomplete legacy profile data | Schema validation at load time catches issues. Missing field defaults apply if safe (e.g., accepted_framing defaults to "romantic"). |

**Schema evolution is additive.** The profile_derivation field on
StoryBlueprint is `None` by default. No existing identity or Blueprint
requires migration.

## Counterfactual acceptance tests

### Test 1 — No profile versus accepted profile

**Same base StoryIdentity.** One has genre_profile=None, the other has
genre_profile with accepted_resolution_contract.

## Risks

1. **Schema coupling**: ProfileDerivation on StoryBlueprint creates a
   dependency between identity and blueprint schemas. Mitigation: optional
   field, None by default.

2. **Staleness complexity**: Profile changes after Blueprint creation
   require staleness detection. Mitigation: Defer full staleness system to
   later phase; first slice only adds diagnostics that flag divergence.

3. **Override precedence confusion**: Two override systems exist:
   StoryIdentity.author_overrides (list[str] of field names) and
   GenreProfileCommitment.author_overrides (list[GenreAuthorOverride] with
   replacement values). Mitigation: First slice uses only
   GenreAuthorOverride. The identity-level overrides are for bypassing
   contract checks, not for profile field replacement.

4. **adherence_posture severity logic**: Severity modification by posture
   adds complexity. Mitigation: Implement simple switch in first slice;
   refine patterns if diagnostic feedback shows false positives.

5. **Existing test breakage**: None expected — all changes are additive and
   backward compatible.

## Open decisions

1. **Should ProfileDerivation be a full Pydantic model or a simpler dict?**
   Recommendation: Pydantic model for schema stability and serialization.

2. **Should the resolution pattern → ending_tone mapping be hardcoded or
   stored in Genre Pack metadata?** Recommendation: Hardcoded in first slice
   (3–5 patterns), moved to pack metadata in a later phase.

3. **Should staleness detection be in the first slice?** Recommendation:
   No. Add diagnostic-only staleness check (content hash comparison) in
   B2 phase.

4. **Should the existing validate_genre_profile_identity() call be added to
   run_all_diagnostics() in the first slice?** Recommendation: No. That is
   B2 from the audit report and can be sequenced after B1f.

## Recommendation

- **First commitment to propagate**: accepted_resolution_contract
- **Blueprint representation**: Integrated into existing
  AuthorAudienceContract fields (expected_elements, forbidden_tropes) with
  a lightweight ProfileDerivation provenance field on StoryBlueprint.
- **Conflict policy**: Policy 3 — profile provides defaults, explicit
  author values always win. Conflicts emit diagnostics.
- **Diagnostic approach**: Three deterministic structural diagnostics
  (D-RES-001, D-RES-002, D-RES-003) checking set membership and pattern
  alignment. Severity modified by adherence_posture.
- **Compatibility strategy**: Additive schema evolution. Identity without
  genre_profile → identical v0.37.1 behavior. ProfileDerivation is None by
  default.
- **Estimated implementation scope**: ~4 days across 6 sub-steps (B1a–B1f).

### Unresolved decisions

2. Full staleness detection system design
3. Integration with generators (deferred to B4 phase)

### Implementation verdict

**Ready for implementation after spec approval.** The accepted_resolution_contract
vertical slice is the smallest meaningful proof of Genre Profile–to–Blueprint
propagation. It requires no NLP, no schema breakage, no Literary-quality
judgment, and no changes to recommendation or acceptance flows. It produces
immediate visible value: authors who accept a Genre Pack will see their
resolution commitments reflected in the Blueprint and validated by
deterministic diagnostics.
