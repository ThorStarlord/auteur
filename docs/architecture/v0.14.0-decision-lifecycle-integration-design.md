# Auteur v0.14.0 — Decision Lifecycle Integration

## Overview

v0.14.0 adds a cross-subsystem **Decision Lifecycle** view that composes
state across planning, simulation, portfolio, commitment, and review to
show where each open decision is in its lifecycle, what gaps exist, and
what the author should do next.

This is the first integration layer above the four vertical pillars built
in v0.10.0–v0.13.0. It does not introduce new state or persistence — it
reads existing stores and composes them into a unified per-decision view.

## Motivation

Until v0.14.0, each subsystem is its own vertical:

- `auteur decision` — workspace for individual decisions
- `auteur simulate` — counterfactual scenario projection
- `auteur portfolio` — optionality and combination generation
- `auteur commit` — immutable intent record and execution planning
- `auteur review` — author review sessions and acceptance
- `auteur plan` — project-level coordination (dependency graph, critical path)

A single open decision can progress through several of these, but no
command shows its end-to-end state. The author must run separate commands
and mentally compose the results.

## Architecture

```
src/auteur/lifecycle/
    __init__.py    — exports
    models.py      — lifecycle stage enums, decision status models
    integrator.py  — probes all subsystems, composes per-decision state
    service.py     — application-service boundary
    cli.py         — argument parsing and rendering
```

The lifecycle integrator probes each subsystem via its existing public
service API. All probes are read-only — no state is created or mutated.

### Probes

| Probe | Subsystem | Method | Data collected |
|-------|-----------|--------|----------------|
| Decision workspace | `DecisionWorkspaceService` | `list_decisions()` / `inspect()` | Open decisions, evidence, readiness |
| Simulation | `SimulationService` | `list_scenarios()` | Scenarios per decision |
| Portfolio | `PortfolioService` | `list_portfolios()`, `inspect()` | Portfolio assignments |
| Commitment | `CommitmentService` | `status()`, `list_commitments()`, `inspect()` | Commitment assignments, state |
| Review | `ReviewService` | `list_sessions()` | Review sessions per decision |
| Planning | `PlanningService` | `status()` | Plan state |

### Decision Lifecycle Stages

```
OPEN → EVIDENCE_GATHERED → SIMULATED → PORTFOLIO → COMPARED
→ PROMOTED → UNDER_REVIEW → ACCEPTANCE_READY → ACCEPTED
                                                     ↓
                                           COMMITTED (zero-or-one)
```

Not all decisions pass through every stage. Commitment is per-portfolio,
not per-decision — a committed portfolio may contain multiple decisions.

### Data model

```python
@dataclass
class DecisionLifecycleStatus:
    decision_id: str
    stage: LifecycleStage
    description: str          # user-facing label
    simulation_count: int     # 0 if none
    portfolio_ids: list[str]  # portfolios containing this decision
    review_session_id: str    # "" if none
    commitment_id: str        # "" if none
    expected: str             # committed candidate
    actual: str               # current candidate
    diverged: bool            # committed ≠ actual
    gaps: list[str]           # missing stage descriptions
```

## CLI surface

```
auteur lifecycle status      — show lifecycle for all decisions
auteur lifecycle inspect ID  — show lifecycle for one decision
auteur lifecycle summary      — aggregate counts per stage
```

## Key decisions

- Read-only composition — no new stores, no events, no mutation
- Stage derivation is deterministic: latest subsystem state wins
- A single decision may appear in multiple portfolios; the latest
  committed portfolio's assignment takes precedence for commitment data
- Gap detection is rule-based: e.g. if a decision has simulation_count=0
  and is not accepted, it has a "not simulated" gap
- No automatic artistic choice — gaps are reported, not auto-filled

## Deferred scope

- Active change notification / subscriptions
- Automated gap filling ("simulate all un-simulated decisions")
- Lifecycle visualization (graph or ASCII art)
- Team/shared lifecycle views
