# Auteur v0.10.0 — Project-Level Narrative Planning and Critical-Path Coordination

## Overview

v0.10.0 adds a deterministic **Project-Level Narrative Planning** subsystem that
coordinates open decisions, review sessions, artifacts, milestones, blockers,
and downstream dependencies across an entire manuscript.

It composes v0.5 impact analysis, v0.7 decisions, v0.8 orchestration, and v0.9
review sessions into a project-wide planning layer. It is not a generic project
manager — it is a narrative planning layer over Auteur's existing artifact,
decision, review, impact, workflow, provenance, and authority systems.

### Central invariant

> **The planner may determine the best justified order in which to address
> project work, but it must never confuse workflow leverage with artistic
> importance or author intent.**

## Plan model

### Plan identity

A project plan has:
- `plan_id`: stable SHA-256 prefix (16 hex chars)
- `project`: project root path
- `horizon`: planning scope (see below)
- `snapshot_id`: source state snapshot reference
- `created_at`: ISO timestamp
- `schema_version`: schema version string
- `tool_version`: Auteur version that created it

### PlanningNode types

| Type | Description | Source |
|------|-------------|--------|
| `DECISION` | An open decision | `DecisionWorkspaceService` |
| `REVIEW_SESSION` | An active review session | `ReviewService` |
| `MILESTONE` | A project milestone | Derived from artifact state |
| `REFRESH` | A required refresh operation | Derived from staleness |

### PlanDependency types

| Type | Strength default | Description |
|------|-----------------|-------------|
| `PREREQUISITE` | HARD | Target must complete before source |
| `BLOCKS` | HARD | Source prevents target from starting |
| `INVALIDATES` | HARD | Source resolution invalidates target |
| `REQUIRES_EVIDENCE_FROM` | SOFT | Source needs evidence from target |
| `REQUIRES_ACCEPTANCE_OF` | HARD | Source requires target acceptance |
| `REQUIRES_REVIEW_COMPLETION` | HARD | Source needs review session completion |
| `REFRESH_AFTER` | SOFT | Source refresh needed after target |
| `SUPERSEDES` | HARD | Source supersedes (replaces) target |

### DependencyStrength

- `HARD`: Blocking — work cannot proceed without resolution
- `SOFT`: Ordering preference — safe to reorder
- `INFORMATIONAL`: No ordering constraint

### DependencyEvidence

Every edge carries:
- `reason`: human-readable explanation
- `source_subsystem`: which subsystem produced it
- `supporting_artifact`: file path or identifier
- `freshness`: evidence freshness

## Planning horizons

| Horizon | Scope | Required structure |
|---------|-------|-------------------|
| `PROJECT` | Entire project | Project identity |
| `BOOK` | Single book | Book metadata |
| `ACT` | Act within a book | Act metadata |
| `CHAPTER` | Single chapter | Chapter metadata |
| `SCENE` | Single scene | Scene metadata |

Horizons are ordered deterministically. Project-level planning works without
act metadata. Chapter planning excludes unrelated chapters. Missing hierarchy
does not cause fabricated scopes.

## Milestone model

Milestones derive from real artifact and authority state:

| Milestone | Criteria |
|-----------|----------|
| Story Identity accepted | story_identity.yaml exists and is accepted |
| Structure valid | Blueprint validates without errors |
| Chapter N realization accepted | Chapter N has accepted realization |
| Chapter N expression accepted | Chapter N has accepted expression |
| Chapter N reasoning current | Chapter N reasoning is non-stale |
| Chapter N reconciliation complete | Chapter N reconciliation closed |
| Act N accepted | All Act N chapters accepted |
| Book assembled | All chapters composed into book |
| Book accepted | Book expression accepted |
| Publication current | Publication is up to date |

States: `NOT_STARTED` | `IN_PROGRESS` | `BLOCKED` | `READY` | `COMPLETED` | `STALE`

## Critical-path definition

Not duration-based CPM. A **narrative blocking critical path** based on graph
structure and milestone impact.

### Node leverage weights

| Factor | Weight |
|--------|--------|
| Directly blocked nodes | 1 per node |
| Transitively blocked nodes | 0.5 per node |
| Blocked milestone (blocking) | 10 per milestone |
| Blocked milestone (in_progress) | 5 per milestone |
| Authority requirement | 3 if author-required |
| Staleness severity | 2 if stale |
| Safe parallel work available | -1 if workaround exists |

The formula is:
```
leverage = (direct_blocked * 1) + (transitive_blocked * 0.5)
         + (blocked_milestones_blocking * 10)
         + (blocked_milestones_in_progress * 5)
         + (authority_required * 3) + (stale * 2)
         - (parallel_workaround * 1)
```

The resulting path is labelled "blocking critical path", not "creative priority".

## Safe parallel work

Two actions are parallel-safe only when ALL of:
1. No hard dependency exists between them
2. No shared authority-bearing target exists
3. No active review session conflict exists
4. Neither action invalidates the other's source state
5. Both actions are independently fresh

## Session coordination

Findings classify session relationships as:
- `COMPATIBLE`: Sessions can coexist
- `ORDER_REQUIRED`: One session should complete before another
- `STALE`: Session evidence is stale
- `CONFLICTING`: Sessions conflict on shared target
- `SUPERSEDED`: Session has been superseded
- `BLOCKED`: Session is blocked by another

## Plan lifecycle

1. **Assembly**: Load real state from all subsystems
2. **Graph construction**: Build dependency graph
3. **Milestone calculation**: Derive milestone states
4. **Critical-path computation**: Find blocking paths
5. **Parallel-work detection**: Find safe concurrent work
6. **Session coordination**: Detect conflicts
7. **Next-action selection**: Determine best ordered action
8. **Snapshot persistence**: Store immutable plan
9. **Refresh**: Reassemble when state changes

### Stale plan handling

A plan is stale when any source state has changed since the plan snapshot.
Stale plans are preserved but marked stale. Actions from stale plans are not
executed. A refresh creates a new plan snapshot.

## Plan persistence

```
.auteur/
  planning/
    snapshots/           — immutable plan JSON snapshots
    history/             — semantic history entries
    latest.yaml          — atomic pointer to current plan
```

Rules:
- Same plan_id + identical content → idempotent
- Same plan_id + conflicting content → explicit error
- Snapshots are immutable once written
- Latest pointer is atomic (atomic write + rename)
- Historical snapshots are never overwritten
- Stale plans remain inspectable

## CLI surface

```
auteur plan status       — show project plan summary
auteur plan graph        — show dependency graph
auteur plan next         — show recommended next action
auteur plan critical-path — show blocking critical path
auteur plan milestones   — show milestone state
auteur plan explain      — explain node or action
auteur plan refresh      — create fresh plan snapshot
auteur plan history      — show plan history
```

Options:
- `--project`, `--json`, `--chapter N`, `--book`, `--act`, `--scene`
- `--save` to persist plan, `--execute` to execute safe actions

## Workflow integration

When a current project plan exists, `workflow next` consumes the plan
recommendation. Dynamic plan consumption with state revalidation before
execution. Safe actions may execute; author-required actions remain refused.
No workflow recursion. Failed child commands do not advance plan state.
