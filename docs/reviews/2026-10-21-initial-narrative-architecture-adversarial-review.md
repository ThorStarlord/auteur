## Verdict

Auteur has a substantial body of narrative-design knowledge, and the current develop request delivers a compact set of relevant composition, authority, emotional, and propagation principles. Delivery remains partial: key distinctions are compressed or absent, and some wording can plausibly steer toward actor-driven or per-genre engines. The effect of these gaps on a real initial candidate is not established.

`ArchitectureCandidate` can represent many legitimate forms, including ensembles, shared mechanisms, non-agent mechanisms, overlapping genres, and abstract temporal phases. Several relationships rely on free-text conventions, however, and the validator checks structure rather than narrative meaning. A real validator probe accepted both a shared non-agent mechanism across two genres and a deliberately disconnected label-only candidate. This confirms expressive flexibility and the validator's claim ceiling; it does not establish that an agent will use the flexibility coherently.

The current initial-generation contract is therefore **undetermined for qualitative adequacy**. The original Tidal Archive request predates the ontology-grounded context; its later revision had both the old candidate and a targeted instruction. Neither proves how the current initial-generation request performs. A fresh, bounded comparison could answer that question, but is deferred until the original private Vision and artifact can be recovered and the compared requests can be preserved.

### Delivery options

| Strategy | Relevance / coherence | Maintenance / auditability | Context cost and freshness effect |
|---|---|---|---|
| Manually curated principles (current) | High relevance and coherent, concise composition guidance; omissions and wording drift are easy to introduce. | Easy to inspect; each principle has a source reference. Manual synchronization is required. | Small. The current `narrative_design_context` is included in `source_sha256`, so editing its principles can make a saved candidate appear stale even when author sources did not change. |
| Selective structured ontology loading | Could deliver precise definitions, relationships and constraints relevant to this Vision; a selector can omit context needed to interpret a fragment or retrieve irrelevant rules. | Direct source traceability is strong, but selection behavior and its tests become another maintained component. A complete ontology dump is not warranted. | Variable and potentially larger. If selected data is added to hashed design context, ontology edits are treated as source freshness changes under today's combined digest. |
| Hybrid: concise principles plus selected ontology excerpts | Best balance: preserve compositional instructions and add only relevant definitions/relationships (for example, Theme, Conflict, Setup/Payoff, and genre-specific concepts when the Vision calls for them). | Auditable if each excerpt carries a stable source reference and selection rationale; keep the principles as the coherent interpretive layer. | Bounded if selection is narrow. Still changes delivered context, so compatibility must be separated from author-source freshness before it can be added safely to the current fingerprint contract. |

**Recommendation:** prefer the hybrid as the eventual delivery architecture, without loading the whole ontology. Keep compact compositional guidance authoritative for how to use concepts; selectively add relevant definitions and relationship meanings, not every genre rule or validator. The recommendation is about delivery design, not an implementation authorization or proof of better output. A prompt-only clarification can be evaluated without first changing freshness because `request_sha256` records the exact prompt and `_SYSTEM` is excluded from `source_sha256`; changing `_DESIGN_PRINCIPLES` or adding selected ontology to the current hashed `narrative_design_context` would continue to couple guidance edits to author-source staleness. Resolve that coupling before expanding dynamic structured delivery.

### Finding classes

- **Confirmed conceptual contradiction:** none found in the current ArchitectureCandidate contract. The Identity-level singular `central_engine` paired with a possible ensemble remains an owner-reserved question, not a proven contradiction.
- **Demonstrated representational limits:** engine-to-genre associations, phase-cycle/disclosure distinctions, and thematic tests are not typed relations. Free text can express them for a reader, but validators and downstream consumers cannot reliably query them.
- **Ambiguities resolvable by convention:** `parent_id` semantics; the three scopes using “governing”; whether `GenreContract.narrative_engine` describes the genre's mechanism use or asserts an independently owned engine; and whether phase `order` is chronology or disclosure.
- **Plausible generation biases, not observed defects:** actor-focused “actor action patterns” wording and a required `narrative_engine` description within each genre contract could steer toward agent causes or per-genre engines. Neither is a schema constraint, and no current fresh candidate has been inspected.
- **Harmless / not applicable omissions absent contrary evidence:** complete genre-specific ontology rule sets and every base-ontology cardinality need not enter a brief, abstract first architecture. Their domain validators govern concrete concept instances elsewhere; no rule says a Studio architecture must instantiate all ontology concepts.
- **Sound existing decisions:** candidate-only authority, explicit acceptance boundaries, free-text links for open-ended abstract relations, and structural validation separate from an artistic quality score. The gaps identified here do not justify replacing those choices.

## Freshness and provenance recommendation

Three separate responsibilities are needed:

1. **Exact request identity.** `request_sha256` identifies the canonical generation payload, including `system`, `user`, and `settings`; it binds a response to what the agent actually received. It does not say whether the response is current.
2. **Author-source freshness.** A distinct digest should cover the Vision, working source material and accepted Identity. If any author-controlled source changes, the dependent proposal must not be applied as though it came from the current commitments. Recheck at response completion and at review/apply so a generated candidate can never silently overwrite changed Identity or Vision.
3. **Generation-guidance provenance and compatibility.** Retain the exact prompt/context identity and runtime/model. Evaluate changes to those instructions separately from changes to author sources. An older pending response remains tied to its exact saved request; when its guidance is no longer compatible, retain it as evidence and require a new proposal before applying. Completed working candidates remain readable with a compatibility indication; changes to guidance alone should not masquerade as author-source staleness. Legacy candidates without enough provenance have unknown compatibility.

The present implementation partially conflates (2) and (3): `_source_fingerprint` hashes both working context and `narrative_design_context`, while `_SYSTEM` is absent from its recomputation. `request_sha256` still protects the response's exact request. Therefore a changed `_DESIGN_PRINCIPLES` value can cause the combined source check to report author-source staleness; a changed `_SYSTEM` alone does not. The request file preserves the exact prompt, but the candidate has no separate guidance-compatibility status. These are confirmed implementation facts; the transition policy above remains a recommendation pending its own decision and tests.

Knowledge-delivery work does not categorically depend on a freshness redesign: a `_SYSTEM`-only wording clarification is already captured by request identity without affecting current source freshness. But edits to `_DESIGN_PRINCIPLES` or dynamically selected ontology context alter the current combined digest and may stale otherwise unchanged author work. Avoid adding dynamic structured context until source freshness and guidance compatibility are separated, or first prove a narrow change can use a prompt-only path without losing source traceability.
